# Implementation and verification status

This file records measured results and remaining release gates. Compilation alone does not establish correct behavior in an input method host.

The actionable backlog is tracked in [TODO](todo.md).

This is a development implementation, not a finished distribution. Ordinary conversion, acknowledged candidate-selection and correction learning, synthetic candidates, native frontends, settings and project dictionaries are implemented. Optional features and native release qualification remain below.

Windows distribution requires native testing of x64 hosts with x64/x86 applications, AppContainer named-pipe access and UILess candidates. ARM64 hosts and the ARM64X forwarder are outside the release scope. macOS requires native testing of InputMethodKit registration, client exceptions, focus preservation, signing and notarization. Developer builds do not imply these distribution requirements have been completed.

| AppContainer hosts on Windows | A frontend inside an AppContainer could open the engine's pipe and still not connect. Before it sends anything a frontend checks which program serves the pipe, as which user and in which session. The first step of that check, reading the session of the serving process, failed there with access denied: a packaged application may not open a process outside its sandbox. A text service in a packaged application or in the search window could therefore neither convert nor ask the engine for anything. Reproduced with a frontend in an AppContainer against an isolated engine: the connection failed with error 5 before the handshake, and a step-by-step probe showed the pipe opening and `ProcessIdToSessionId` refused. When it starts, the engine now grants every package the rights to read its image name and exit status and to read its token. The same probe then passed every step, including opening the process and its token. The sandbox is made without registering anything: an ordinary process is created suspended and its token is replaced by an AppContainer token without capabilities before it runs. Passed after the change: the contract test `windows_sandbox`, in which that frontend connects, types a word and commits it as kana, together with the existing pipe and supervisor contracts. That test then failed on about one in four CI runners, and on such a runner every time: inside the AppContainer the system reported the engine by its native path (`\Device\HarddiskVolume6\...`) instead of `D:\...`, the volume of the checkout, so the comparison with a path with a drive letter refused the engine. The same query from the test process returned the `D:` path. Frontends now name the engine by the native path beside their own file and compare native paths. Passed after that change: the same contracts, and in the sandbox a refusal of a program of the same name in another folder. ## Remaining implementation

These are not implemented or advertised as working:

- Live conversion, LLM-generated candidates and automatic model download. Local inference currently reranks existing Mozc choices only. Live conversion and automatic writing assistance settings remain rejected.
- Automatic post-commit writing indicators, frontend panel invocation, verified document replacement and acceptance records. Explicit writing review only reports findings.
- Automatic vocabulary promotion. Explicit dictionary editing is available in settings and the CLI; correction records can prefill a reviewed registration form. Automatic promotion needs ranking-impact measurements before selecting its size budget. Candidate-specific history deletion is limited to the selected upstream first candidate until Mozc's other-index erasure can preserve unrelated terms. Separate bulk clears are available through settings and the CLI; Kanade deletion does not erase Mozc's independent learning.
- Project comment/string vocabulary. Settings can approve folders, create/rebuild dictionaries, edit readings and application scopes, opt into automatic updates, enable/disable and revoke approvals. Declared identifiers use the bundled technical readings; general English pronunciation beyond that table and user overrides remains unavailable. Unlisted Latin parts use spelling readings. Manual incremental scans do not yet share all full-scan exclusions ([astro-sight #395](https://github.com/owayo/astro-sight/issues/395)); monitoring uses full scans. Windows notifications are disabled because the current backend can silently lose a watch on overflow; use explicit indexing and `reload-projects` there until a reliable backend is implemented and qualified.
- hasami overlays, reading-constrained analysis and token-origin/proper-noun APIs needed for model validation. The extension covers kana normalization, dependency classification and term shape.
- Configurable command chains and left/right modifier mappings, vertical candidate layout, complete theme configuration and frontend learning-rollback shortcuts. Basic F6–F10 character conversion and calculated week/month-end dates are available. Mozc already supplies common current-date candidates; its output was checked separately.
- Qualification of the macOS registration/LaunchAgent installer, idle/startup lifecycle, notarized installer/update flow, and singleton routing of multiple settings launches.
- Qualification of the Windows EXE/MSI, architecture registration/update rollback and engine startup policy. The release targets x64 Windows, including the x86 TIP. ARM64 and ARM64X are outside the release scope; their source remains unqualified.
