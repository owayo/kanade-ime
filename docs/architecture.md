# Architecture

Release installers target Windows x64 and Apple Silicon macOS. Windows uses a WiX Burn EXE containing the MSI; its native bootstrapper, MSI and whole EXE are signed separately. The Windows MSI stages both x64 and x86 TSF implementations, keeps management and engine executables adjacent, and schedules registration and rollback in the installer transaction. Its CI rehearsal uses a disposable runner and a temporary engine profile. Registration cleanup attempts all categories, the language profile and COM keys before returning an error. ARM64 forwarding remains outside the release matrix.

The macOS DMG contains a signed AppKit installer with the IME payload nested under Contents/Helpers. This keeps it self-contained during app translocation. A background task verifies the payload signature before invoking the dedicated Rust installer; the UI does not copy files or register input sources itself. Both app tickets are stapled before building the signed and notarized DMG. The installer has the same macOS 14 minimum as the IME. It reuses the source installer's input-source handoff and bundle replacement, accepts an explicit absolute bundle path, and needs no source checkout. Installation checks the app identity and certificate signature before replacement. Uninstall checks the app identity and LaunchAgent binding before stopping anything, retains personal data, and attempts to restore the agent if removal fails while the app remains. Release jobs require credentials and successful CI before tagging; ordinary builds and dry runs do not change release metadata.

Kanade uses three independent components during ordinary input: the native frontend, a Rust engine, and an unmodified Mozc worker. The engine owns conversion sessions; the worker owns the isolated Mozc profile. Cargo does not invoke Bazel. `mise run build-worker` is an explicit upstream build step.

Each key is processed synchronously. Version negotiation precedes input. Connection and context epochs reject old replies. Event sequences are strictly increasing; a retry returns the previous response only when the request is identical. A successful document acknowledgement makes a commit eligible for Kanade learning. An unacknowledged commit is never replayed after reconnecting.

Candidate identifiers are local to the current Mozc segment. Only opaque, revision-scoped handles cross the frontend boundary. A selection resolves its current candidate again before submission. Synthetic commits reset Mozc composition rather than reverting earlier learning.

Explicit Mozc choices from clicks, candidate digits and navigation retain at most 32 reading/surface intents in a composition. Only chosen terms present in a successful document acknowledgement reach learning. Defaults, transliteration, cancellation, transient commits and private/unknown contexts are excluded. The background service aggregates a bounded term's selection count under a stable record ID, independently of morphology. A persistent store-local sequence makes recency survive restart: the latest deliberate choice gets a bonus above the capped frequency score; other choices use frequency with recency as a tie-breaker. Preferences rank existing ordinary candidates and never create vocabulary. A key uses one preference snapshot for both its selected surface and its candidate order; that order stays frozen for the displayed list. Accepting its default does not reinforce it. Snapshot preparation and retired memory release stay outside the publication lock. At most 1,024 receipt journals support deletion rollback; out-of-order rollback rebases later journals so it cannot restore an erased contribution. Failed saves retain the prior published store.

Ctrl+Delete is intercepted before the upstream keymap can implicitly erase a different focused candidate. In normal contexts it resolves the displayed Mozc choice again and permits only upstream index zero: the pinned segment-history rewriter ignores nonzero indexes. Private, unknown, synthetic, transliteration, invisible and other-index choices are consumed without deletion. Successful removal returns to the reading without automatically reconverting or committing punctuation. It does not delete the dictionary entry or Kanade correction records. The explicit erasure is outside document-ACK rollback; only an unacknowledged real Mozc commit is reverted on a failed edit. History synchronization remains an idle operation, so unsynced erasure is not guaranteed to survive transport/process failure. Reply retry caches retain event commits; the steady session snapshot never carries a commit into a later preview or no-op command.

Password input bypasses conversion. Unknown and private input disables persistent learning before a key reaches Mozc. Context is bounded, ephemeral, and cleared on focus changes. Optional language analysis, model inference, indexing, disk compaction and settings UI stay off the key path. No runtime component sends input to a network service.

Calculated week/month-end dates use a background local-calendar observation. Its validity ends at the next local midnight or ninety seconds after observation, whichever comes first; backwards wall-clock jumps also invalidate it. Keys read only the cached date and wall-clock timestamp, with no time-zone or file access. An already displayed date stays bound to that composition's reading. New compositions require a valid observation. Calendar choices replace the entire matching reading, including multiple Mozc segments, and their transient commits enter neither correction detection nor delayed Mozc history insertion. Common relative days remain Mozc's responsibility. The native settings toggle and authenticated configuration control calendar generation.

Synthetic previews retain their original backend snapshot and candidate ordering. Navigation can return to ordinary candidates without losing segments. Typing after a synthetic preview first commits the displayed choice, then processes the new key; any resulting commit/preedit is returned as one acknowledged event. A mixed event tracks whether the new key produced a real Mozc commit so a failed document edit reverts only that operation. No retry reexecutes the chain.

Emoji readings are generated explicitly from six digest-pinned datasets and the separately pinned IPAdic dictionary. Unicode fully-qualified sequences provide output spellings; source identity removes only variation selectors. The immutable catalogue is loaded during engine initialization. Keys perform bounded exact lookups on the whole reading/surface, then on a focused segment of at least three characters when the whole lookup misses. At most 32 catalogue choices follow the first six ordinary choices; existing equivalent emoji are replaced in place and deduplicated. Previews retain the original backend composition, and segment navigation/cancellation ends that preview before a new candidate set is built. Catalogue commits are transient, including a continued-input event containing their prefix, so neither correction evidence nor delayed Mozc history insertion stores them. The setting controls these additional choices; upstream emoji rewriting remains available. Generation, fetching, morphology, checksums and notices are outside the key path. Data generation validates its complete staging directory before publication and leaves the existing catalogue in place on a source/checksum failure.

A connection and its worker are kept for as long as they are healthy. The engine places no limit on how long a connection stays quiet: it waits for the first byte of a frame indefinitely, then requires the whole frame within two seconds, so a stalled or fragmented frame is bounded and an idle frontend is not. The number of connections is bounded by admission limits, not by time. A full table refuses a new connection instead of evicting an existing one: a paused composition keeps its transport. A frontend notices an already closed connection before sending its next key and opens another.

Time limits detect a peer that stopped answering. They are not latency targets, and a reply inside its limit is delivered however slow it is. The worker calls made for one key share 400 ms. A call outside input (history sync, settings, session open and close, administration) has one second, because it touches the disk. A queued request is refused unprocessed after 1.1 seconds, a connection waits 1.75 seconds for the engine, and a frontend waits two seconds for its whole exchange. Each outer limit exceeds the limits inside it with a margin, so a failure normally arrives as an explicit reply. Scheduling can exceed any finite limit; recovery stays correct when an outer limit expires first. Exceeding a worker limit kills the worker, which ends every session, so only a worker that stopped answering or whose pipe broke is replaced. A failure confined to one session, such as a rejected document edit, ends that session and leaves the worker and the other compositions running. History sync waits while any composition is displayed, for at most five minutes. A failed worker replacement is retried twice before the engine exits.

The worker has no Command modifier, so a Command chord is never forwarded to it; without that rule the chord would be typed into the composition as a letter. A key the frontend left to the application cannot start a composition: if the worker consumed it while nothing was composed, the engine discards that composition and reports the key unused.

When a session is lost while a composition is displayed, the frontend holds it. The document keeps its marked text and the frontend keeps the last reading the document acknowledged. The key whose exchange failed is used up and is never sent again. A hold does not end by itself: no timeout, retry limit or age inserts text. It ends when a new session accepts the reading, when the user presses Enter (the reading is inserted) or Escape (the composition is removed), or when the focus, input source or document ends (the reading is inserted). A hold never commits an unapproved conversion, and a password context discards it.

Protocol version 3 adds a restore request for the first case. It is valid only as the first event of a connection, carries the acknowledged reading and the current context, and follows the rules of a key: revision and sequence checks, a cached reply for an identical retry, and a document acknowledgement before the next event. The engine switches learning off for private and unknown contexts before the reading reaches the worker, refuses a password context, and never commits or learns from a restore. The worker reports romaji still waiting for its vowel as fullwidth Latin at the end of a reading; kana before it is inserted as composed text and the waiting letters are typed again, so they still combine with the next key. The result must equal the requested reading, with no commit and no conversion. Otherwise the session is reset and the restore refused. After a refusal, three failed attempts, or with an engine older than version 3, the frontend stops trying and the composition stays for the user's Enter or Escape. A frontend that leaves without acknowledging a commit has the worker's learning from that commit reverted.

Transport, recovery and process-exit diagnostics are bounded files of predefined events: `engine-events.log` and `input-events.log` beside the settings logs. A record is a timestamp, a process ID, an event name and a repeat count. The recording call only queues, so the key path performs no file I/O; a background thread writes and collapses a run of one event into one line and one count, which prevents one line per key during an outage. No API accepts text, so input, keys, application or document identifiers, paths and error messages cannot be recorded. The engine records the stage at which it exits. An instance started with its own data directory writes these files there.

The default configuration has neither live conversion nor a language model. The optional local model reranks existing Mozc candidates in a separate CPU worker, with a bounded background queue. Model import requires explicit license and local-processing consent, a pinned file digest, independent tokenizer parity, ranking fixtures and latency gates. Qualification binds the model, vocabulary, runtime executable, prompt and corpora; changes require qualification again. The Windows and macOS installers include the pinned model for offline import. [Local model details](llm.md) describe the limits and qualification procedure.

Kanade builds the Tsumugi prompt, vocabulary fingerprint, end token and qualification rules into the engine and worker. The settings window displays the fixed identity and binds consent to its terms. Import verifies the exact GGUF digest before running qualification.

After acknowledging its key reply, the frontend polls for candidate refinement. A focused native frontend may also send the next event sequence to receive and acknowledge a sentence preview. A candidate-only response preserves the key sequence. A sentence preview advances it and follows the document acknowledgement protocol. A new revision retires old candidate handles. New keys, manual navigation, focus changes, resets and expired results cancel refinement. Native frontends poll every 60 ms while the result is pending and stop after the 700 ms scoring deadline with a small scheduling margin. The candidate footer reports active scoring, completion (including an unchanged order), a failed evaluation, or expiry. Terminal status alone preserves the candidate handles. Inference never delays the synchronous key response. Normal, non-excluded contexts with learning enabled may submit a bounded left context; private, unknown, password and sensitive contexts do not. Native candidates are independent of GPUI; settings UI exists only while a user window is open.

hasami analyzes acknowledged corrections on the learning thread, classifying term shape before records are updated. Its kana normalization also supplies keys for correction learning, project vocabulary and emoji lookup. It does not replace Mozc's conversion engine. Reading-constrained analysis of newly generated model output remains unimplemented; the current model produces scores for existing candidates only.

The signed IMK bundle declares its bundle-scoped `.Connection` service in `InputMethodConnectionName`. Startup reads this value from the bundle and rejects a mismatch with its bundle identifier before starting the server. The signed-bundle self-check validates the same configuration. An unrelated legacy connection name can leave native clients unable to obtain the IME endpoint even when another host can type.

Each IMK controller retains its settings menu and item for its lifetime, preserving their identity during repeated system-menu requests. The controller implements the custom settings action and the legacy Preferences callback using the same launcher. Menu enabling is explicit. On the qualified macOS version, InputMethodKit invokes the action directly rather than the controller's `doCommandBySelector:commandDictionary:` override; the action's dispatch event is the delivery evidence. LaunchServices activates the bundled settings application; a reopen callback reuses its window. The window is created before background configuration and learning-record requests, so connection failures remain visible and retryable. Until settings load successfully, default values cannot be saved. macOS settings lifecycle diagnostics accept only predefined events, timestamps and process IDs, with a bounded private file per component. Selector names and command dictionaries are never logged. Menu construction performs no diagnostic I/O because the system can request the menu during ordinary input. Diagnostic writes occur only during explicit settings actions or settings-window lifecycle.

The settings window answers every explicit open request. GPUI forwards a reopen request only while no window is visible, so a window on another Space or display would not be shown again. The settings application therefore registers its own handler for the reopen Apple event; GPUI's callback remains as a fallback. A new window opens on the display under the pointer rather than always on the primary display. A later request restores a minimized window, and moves a window from another display, or from outside every display, to the pointer's display. A window already reachable there keeps the position the user chose, and a full-screen window is never moved. The window follows the active Space on activation and is ordered front within the normal level even before the application becomes active. It never raises its level, so another application's always-on-top window can still cover it. Native frame and ordering changes run outside GPUI updates because AppKit notifies GPUI's window delegate synchronously. Display selection and repositioning are pure functions with multi-display tests. Shortly after presenting, the window records whether it is visible, fully occluded or off the active Space, using predefined events only. An application menu provides Close, Minimize and Quit.

Local macOS updates require finished composition. The installer validates and stages a signed bundle before selecting an already enabled ASCII layout when Kanade is selected. Fresh helpers deliver TIS notifications before reading the selection cache and confirm the change with a bounded wait. A failed confirmation prevents bundle replacement. Updates normally terminate the matching IME and settings applications, then replace the bundle and restart the engine. Successful updates leave ASCII selected; a concurrent user selection is retained. Failed updates attempt to restore the original mode and report an unconfirmed restoration. A per-directory file lock excludes concurrent installers. Full composition/ACK draining and interruption recovery remain separate qualification work.

Input-source diagnostics filter the unqualified system-enabled list by bundle identity. A bundle-filtered query can include a mode that has no enabled record after a mode-ID migration. Diagnostics report the enabled mode IDs explicitly. An already enabled parent without its input mode is reported as stale; automatic enabling refuses that state and directs the user to remove and re-add Kanade in System Settings. Registration never toggles an existing mode off and on to repair it: that legacy API sequence can rewrite unrelated source preferences from a stale snapshot.

The [private worker protocol](worker-protocol.md) provides a dictionary-only background loader that preserves conversion/prediction history. Its generation-scoped status is independent of input event sequencing. Ordinary upstream protocol messages and the pinned source tree remain unchanged. Authenticated management serializes explicit edits through a lazily started background service. It compares the expected file revision, holds a writer lock, and prepares an immutable, synced replacement without dropping unknown protobuf data. The engine admits only its atomic rename, after every composition and document acknowledgement completes and input has been idle for two seconds. Cancellation races with publication through one atomic permit. Parsing, hashing, file/directory sync and cleanup stay on the management thread. Writer guards explicitly unlock before closing their file: a concurrent process spawn may briefly inherit the open file description. Jobs retain metadata only; a saved revision distinguishes failed reloads from unsaved edits. Explicit promotion reads an acknowledged correction record. Automatic promotion remains disabled pending ranking-budget measurements.

The native settings dictionary panel uses that same authenticated management service on background tasks. An in-memory draft is bound to the exact revision and entry/dictionary positions it displayed; refresh never rebases it onto a different revision. Submission freezes its fields, and an unknown result is not automatically replayed. Polling distinguishes an unsaved failure from a saved file whose engine reload failed. Correction records can prefill a registration form, but only an explicit Save submits it. Text fields implement native UTF-16 selection, marked text and candidate geometry; publication is blocked while a field is composing. No draft is written to diagnostic logs or autosaved. Closing an editable draft requires an explicit discard choice.

Learning defaults to all known application identities, except those in `learning_excluded_apps`. Empty, malformed and unknown identities remain unknown; private and password contexts never become normal merely because an application is not excluded. Loading a legacy settings file discards its former `learning_apps` allowlist without interpreting it as exclusions, preserving the learning switch, other settings and any explicit new exclusions. Subsequent saves write only the new field.

The authenticated exclusions operation compares the exact previous exclusion list under the settings lock and merges only that list into the current configuration; the former allowlist operation is refused rather than reinterpreted. A stale draft cannot overwrite another app-scope edit or unrelated settings. The native editor requires review, invalidates it on edits, blocks submission during marked text and freezes a submitted draft. It reads an uncertain outcome back without replaying it. Closing an unsubmitted draft presents a fixed, visible discard choice. The macOS chooser reads the selected bundle's identifier without loading its code.

Welcome adds an optional learning policy with an enabled flag and exclusions, retaining an empty legacy allowlist so an older frontend fails closed. New frontends retain the old allowlist behavior when connected to an older engine with no policy. No field numbers or key-event versions change. Frontends adopt policy changes on reconnection; source switching refreshes an existing client. Engine privacy gates enforce exclusions before any key, selection or restore reaches Mozc, and again before ACK-based learning, so stale clients cannot continue to learn in an excluded application. Applying an exclusion also clears pending selection intents, correction state, ephemeral left context and queued refinement for that session.

Settings buttons, switches and model choices share persistent, element-keyed focus handles. The window root has a non-tab-stop focus handle so global Tab and Shift-Tab bindings work before any control is selected. Traversal follows render order; focused controls have a visible style and request scrolling only on focus transitions. Scroll bodies scope these requests and defer a bounded ScrollHandle offset update because this GPUI version implements immediate autoscroll only for List. Enter and Space use GPUI's release-time activation, including its focus-generation check; the application does not synthesize clicks. Inactive controls retain their accessible role with an availability description, leave the tab order and suppress both mouse and keyboard callbacks. Native text fields retain their more specific marked-text key map, gain their own visible focus and scroll request, and do not bind Enter to submission.

Project source monitoring defaults off for every approval. An explicit settings toggle enables it across engine starts; a separate CLI watch remains available. The engine starts the optional coordinator off the input thread. It observes only opted-in, enabled roots whose persisted directory binding still matches. Unreadable approvals stop monitoring, and disabled, revoked or replaced roots cancel their automatic job. A bounded observer retains dirty project identities, never event paths or source excerpts. Registry and root metadata are rechecked every two seconds; notification overflow/errors rebuild observers and require full scans. Automatic jobs share the index service with manual jobs. At most one analysis runs, with room for one manual request behind an automatic publication. A manual request cancels cancellable automatic work; publication already admitted finishes first. Oldest dirty projects run first so frequently edited folders cannot starve others. Notifications settle for 500 ms, bounded by two seconds of continuous changes. Scans use the analyzer's complete ignore rules; each successful run waits at least two seconds or four times its duration before the next scan. Failures retain the previous generation and back off from five to 300 seconds. Analyzer children run at lower priority with two analysis threads; engine priority stays unchanged. Index publication is serialized per project and rechecks the approval binding and root identity. Immutable generations carry their approval ID, so reusing a project ID cannot expose orphaned vocabulary. Incremental indexing without a valid base performs a full scan. Registry writes reject stale snapshots. Revocation is durable before generation cleanup. The engine observes only project data, loading and serializing catalogue updates off the key path; unreadable approvals disable project vocabulary. Transient generation-read failures may retain only an identical approval's snapshot and schedule a retry. Old catalogue memory is released on the reloader thread. Selecting an older displayed project candidate rechecks the current app-scoped catalogue before committing. Windows notifications are disabled pending a reliable backend; explicit indexing and management reload remain available.

Project approval from settings is a separate, explicit background workflow. Preparation canonicalizes the selected folder and binds its directory identity, registry revision, project ID and complete app scope in an in-memory preview; it grants no approval and performs no scan. Four previews expire after five minutes, with older previews evicted on repeated review. Submission consumes the preview once and rechecks its binding before saving approval. The persisted optional directory binding prevents a replacement folder from inheriting the permission; legacy approvals without that field remain readable. A failed or cancelled first scan retains an explicitly saved approval and reports that partial state. Rebuilds bind the exact enabled project snapshot before reading and publication. One analysis runs at a time; sixteen statuses retain only opaque identities, fixed state/reason values, counts and revision/reload flags. They contain no source vocabulary, folder paths or app identifiers. Cancellation and publication compete for one atomic permit. Failed or cancelled scans leave the previous generation unchanged. Read-only status recovery never resubmits an uncertain approval.

The macOS bundle contains the pinned analyzer and its dependency notices. Installed engines use that signed sibling rather than searching PATH; an explicit development override remains available. Each invocation forces a private fixed configuration with debug logging disabled, limits analysis threads to two, bounds output to 8 MiB and waits at most 35 seconds per request, including blocked request writes and response reads. Cancellation terminates the owned analyzer. Analysis, file access and catalogue reload stay outside the synchronous key path. Project lookups prefer an exact whole-reading match before falling back to the focused segment; whole matches replace the entire matching reading, including multiple Mozc segments. Selection still revalidates the current app-scoped catalogue.

Project application scopes can be replaced through authenticated management without changing the approved directory or approval identity. A scope query binds the registry revision and approval, returns at most 64 application IDs, and excludes source terms and reading overrides. The settings editor keeps its draft in memory and requires confirmation of the complete target list. Editing after confirmation invalidates it; saving freezes the fields, submits once and reads back the same approval's actual scope. An uncertain write is never retried automatically. Concurrent edits and reapprovals reject the stale revision. On macOS the file chooser reads the selected application's bundle metadata on a background task without loading its code. Removing an app immediately makes previously displayed project candidate handles invalid there; rescanning source files is unnecessary for a scope-only change.

Settings can list, enable, disable and revoke existing project approvals through authenticated management. Edits carry both the registry revision and approval identity; they cannot approve another directory or change application access. Lists contain bounded display metadata and counts, without exporting identifier-reading overrides. File access and catalogue reload run outside rendering and input handling. The view reloads its list after an edit, including an uncertain response, rather than replaying it. Revocation saves the registry first; cleanup only removes recognized generated files outside every approved source root. An unsafe or failed cleanup preserves the files and reports that state separately from the saved approval change.

On Windows, input hosts may connect from the current user and logon session, including AppContainer hosts. Settings and stored-learning management additionally require the client process to be the installed sibling `kanade-ui.exe`, identified through the pipe's kernel-reported process ID. Conversion access alone does not grant management access.

Project reading management exposes only revision/approval-bound pages of fifty explicit overrides. Stored entries and edits are validated as bounded identifier/kana pairs; summary and monitoring replies never export the vocabulary. A reading job saves its exact revision once, then rebuilds through the same queue. Cancelling or failing after the save retains that setting and reports the saved revision while preserving the previous generation. The native editor confirms the identifier and reading, invalidates confirmation on edits, freezes submitted fields and protects unsubmitted drafts on navigation and close. Clearing an override requires the same explicit review and rebuild.

The offline candidate exporter creates a fresh private profile and a separate session per authored request. It enumerates focused candidates for every original segment without selecting or submitting them, preserves the reading and first surface, and emits one JSON Lines response per request. Request rows are bounded to 64 KiB; oversized rows are drained without retaining their remainder. Diagnostics contain row numbers and fixed error categories only. Artifact identity comes from the verified worker manifest and pinned upstream lock. A source commit is emitted only for a clean Git build. Offline request timeouts and suggestion suppression are explicit adapter settings; the default remains the existing worker timeout, input-event deadlines still cap all calls, dictionary controls retain their bound, and restart preserves the offline settings.

Windows build tooling retains canonical filesystem paths internally and converts Git and Bazel path arguments from the Win32 verbatim namespace to forward-slash drive or UNC paths. Path extraction removes only the three known environment-assignment diagnostics emitted by the pinned Windows wrapper and rejects missing or ambiguous values. Worker staging resolves and canonicalizes cquery output against Bazel's execution root rather than assuming workspace convenience links exist. The explicit `cargo xtask check-bazel-paths` rehearsal uses a small disposable workspace with the unchanged upstream Windows wrapper and those links disabled, and also clones a local Git repository through the same argument normalization; CI checks it on Windows before compiling the full worker. This normalization is outside ordinary Cargo builds and never changes the pinned upstream tree.

Windows TSF category and input-processor registrations are shared across architectures, while COM class registrations belong to each registry view. DLL removal enumerates TSF membership before unregistering it, so the second architecture and repeated removals skip registrations already removed by the first. Failures still propagate and do not prevent the other cleanup steps from being attempted. A disposable Windows job builds only the two real input DLLs and exercises both removal orders and repeated removal before the full worker build. Full installer tests retain the original failure, attempt both EXE and MSI cleanup, and read process exit codes through retained process handles.
