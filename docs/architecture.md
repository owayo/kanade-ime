# Architecture

Release installers target Windows x64 and Apple Silicon macOS. Windows uses a WiX Burn EXE containing the MSI; its native bootstrapper, MSI and whole EXE are signed separately. The Windows MSI stages both x64 and x86 TSF implementations, keeps management and engine executables adjacent, and schedules registration and rollback in the installer transaction. Its CI rehearsal uses a disposable runner and a temporary engine profile. Registration cleanup attempts all categories, the language profile and COM keys before returning an error. ARM64 forwarding remains outside the release matrix.

The stable macOS DMG contains a signed AppKit installer with the IME payload nested under Contents/Helpers. This keeps it self-contained during app translocation. A background task verifies the payload signature before invoking the dedicated Rust installer; the UI does not copy files or register input sources itself. Both app tickets are stapled before building the signed and notarized DMG. The public preview uses an unsigned PKG in the current-user installation domain. Its postinstall verifies the extracted, certificate-signed app before invoking the same helper. Preview registration can be retried after sign-in when the engine is running and only input-source registration failed. Both installers require macOS 14 and reuse the source installer's input-source handoff and bundle replacement. Uninstall checks the app identity and LaunchAgent binding before stopping anything, retains personal data, and attempts to restore the agent if removal fails while the app remains. Stable publication requires credentials and successful CI before tagging; ordinary builds and dry runs do not change release metadata.

Kanade uses three independent components during ordinary input: the native frontend, a Rust engine, and an unmodified Mozc worker. The engine owns conversion sessions; the worker owns the isolated Mozc profile. Cargo does not invoke Bazel. `mise run build-worker` is an explicit upstream build step.

Each key is processed synchronously. Version negotiation precedes input. Connection and context epochs reject old replies. Event sequences are strictly increasing; a retry returns the previous response only when the request is identical. A successful document acknowledgement makes a commit eligible for Kanade learning. An unacknowledged commit is never replayed after reconnecting.

Candidate identifiers are local to the current Mozc segment. Only opaque, revision-scoped handles cross the frontend boundary. A selection resolves its current candidate again before submission. Synthetic commits reset Mozc composition rather than reverting earlier learning.

Explicit Mozc choices from clicks, candidate digits and navigation retain at most 32 reading/surface intents in a composition. Only chosen terms present in a successful document acknowledgement reach learning. Defaults, transliteration, cancellation, transient commits and private/unknown contexts are excluded. The background service aggregates a bounded term's selection count under a stable record ID, independently of morphology. A persistent store-local sequence makes recency survive restart: the latest deliberate choice gets a bonus above the capped frequency score; other choices use frequency with recency as a tie-breaker. Preferences rank existing ordinary candidates and never create vocabulary. A key uses one preference snapshot for both its selected surface and its candidate order; that order stays frozen for the displayed list. Accepting its default does not reinforce it. Snapshot preparation and retired memory release stay outside the publication lock. At most 1,024 receipt journals support deletion rollback; out-of-order rollback rebases later journals so it cannot restore an erased contribution. Failed saves retain the prior published store.

Ctrl+Delete is intercepted before the upstream keymap can implicitly erase a different focused candidate. In normal contexts it resolves the displayed Mozc choice again and permits only upstream index zero: the pinned segment-history rewriter ignores nonzero indexes. Private, unknown, synthetic, transliteration, invisible and other-index choices are consumed without deletion. Successful removal returns to the reading without automatically reconverting or committing punctuation. It does not delete the dictionary entry or Kanade correction records. The explicit erasure is outside document-ACK rollback; only an unacknowledged real Mozc commit is reverted on a failed edit. History synchronization remains an idle operation, so unsynced erasure is not guaranteed to survive transport/process failure. Reply retry caches retain event commits; the steady session snapshot never carries a commit into a later preview or no-op command.

Password input bypasses conversion. Unknown and private input disables persistent learning before a key reaches Mozc. Context is bounded, ephemeral, and cleared on focus changes. Optional language analysis, model inference, indexing, disk compaction and settings UI stay off the key path. No runtime component sends input to a network service.

Calculated week/month-end dates use a background local-calendar observation. Its validity ends at the next local midnight or ninety seconds after observation, whichever comes first; backwards wall-clock jumps also invalidate it. Keys read only the cached date and wall-clock timestamp, with no time-zone or file access. An already displayed date stays bound to that composition's reading. New compositions require a valid observation. Calendar choices replace the entire matching reading, including multiple Mozc segments, and their transient commits enter neither correction detection nor delayed Mozc history insertion. Common relative days remain Mozc's responsibility. The native settings toggle and authenticated configuration control calendar generation.

Synthetic previews retain their original backend snapshot and candidate ordering. Navigation can return to ordinary candidates without losing segments. Typing after a synthetic preview first commits the displayed choice, then processes the new key; any resulting commit/preedit is returned as one acknowledged event. A mixed event tracks whether the new key produced a real Mozc commit so a failed document edit reverts only that operation. No retry reexecutes the chain.

Emoji readings are generated explicitly from six digest-pinned datasets and the separately pinned IPAdic dictionary. Unicode fully-qualified sequences provide output spellings; source identity removes only variation selectors. The immutable catalogue is loaded during engine initialization. Keys perform bounded exact lookups on the whole reading/surface, then on a focused segment of at least three characters when the whole lookup misses. At most 32 catalogue choices follow the first six ordinary choices; existing equivalent emoji are replaced in place and deduplicated. Previews retain the original backend composition, and segment navigation/cancellation ends that preview before a new candidate set is built. Catalogue commits are transient, including a continued-input event containing their prefix, so neither correction evidence nor delayed Mozc history insertion stores them. The setting controls these additional choices; upstream emoji rewriting remains available. Generation, fetching, morphology, checksums and notices are outside the key path. Data generation validates its complete staging directory before publication and leaves the existing catalogue in place on a source/checksum failure.

A connection and its worker are kept for as long as they are healthy. The engine places no limit on how long a connection stays quiet: it waits for the first byte of a frame indefinitely, then requires the whole frame within two seconds, so a stalled or fragmented frame is bounded and an idle frontend is not. The number of connections is bounded by admission limits, not by time. A full table refuses a new connection instead of evicting an existing one: a paused composition keeps its transport. A frontend notices an already closed connection before sending its next key and opens another.

Time limits detect a peer that stopped answering. They are not latency targets, and a reply inside its limit is delivered however slow it is. The worker calls made for one key share 400 ms. A call outside input (history sync, settings, session open and close, administration) has one second, because it touches the disk. A queued request is refused unprocessed after 1.1 seconds, a connection waits 1.75 seconds for the engine, and a frontend waits two seconds for its whole exchange. Each outer limit exceeds the limits inside it with a margin, so a failure normally arrives as an explicit reply. Scheduling can exceed any finite limit; recovery stays correct when an outer limit expires first. Exceeding a worker limit kills the worker, which ends every session, so only a worker that stopped answering or whose pipe broke is replaced. A failure confined to one session, such as a rejected document edit, ends that session and leaves the worker and the other compositions running. History sync waits while any composition is displayed, for at most five minutes. A failed worker replacement is retried twice before the engine exits.

The worker has no Command modifier, so a Command chord is never forwarded to it; without that rule the chord would be typed into the composition as a letter. A key the frontend left to the application cannot start a composition: if the worker consumed it while nothing was composed, the engine discards that composition and reports the key unused.

When a session is lost while a composition is displayed, the frontend holds it. The document keeps its marked text and the frontend keeps the last reading the document acknowledged. The key whose exchange failed is used up and is never sent again. A hold does not end by itself: no timeout, retry limit or age inserts text. It ends when a new session accepts the reading, when the user presses Enter (the reading is inserted) or Escape (the composition is removed), or when the focus, input source or document ends (the reading is inserted). A hold never commits an unapproved conversion, and a password context discards it.

Protocol version 3 adds a restore request for the first case. It is valid only as the first event of a connection, carries the acknowledged reading and the current context, and follows the rules of a key: revision and sequence checks, a cached reply for an identical retry, and a document acknowledgement before the next event. The engine switches learning off for private and unknown contexts before the reading reaches the worker, refuses a password context, and never commits or learns from a restore. The worker reports romaji still waiting for its vowel as fullwidth Latin at the end of a reading; kana before it is inserted as composed text and the waiting letters are typed again, so they still combine with the next key. The result must equal the requested reading, with no commit and no conversion. Otherwise the session is reset and the restore refused. After a refusal, three failed attempts, or with an engine older than version 3, the frontend stops trying and the composition stays for the user's Enter or Escape. A frontend that leaves without acknowledging a commit has the worker's learning from that commit reverted.

Transport, recovery and process-exit diagnostics are bounded files of predefined events: `engine-events.log` and `input-events.log` beside the settings logs. A record is a timestamp, a process ID, an event name and a repeat count. A few events carry one more value: an exit code, a restart count, or the thread and source line where a panic started. The recording call only queues, so the key path performs no file I/O; a background thread writes and collapses a run of one event into one line and one count, which prevents one line per key during an outage. No API accepts text, so input, keys, application or document identifiers, paths and error messages cannot be recorded. A panic is recorded by the position the compiler assigned to it. Its message can quote the text that was being processed, so it is never read, and a release build does not print it. The engine records the stage at which it exits. An instance started with its own data directory writes these files there.

On Windows the engine is built for the windowed subsystem and owns no console. A console window can be closed, and closing it ends every attached process at once, without a record; an engine that a sign-in entry started directly disappeared that way. The workers and the analyzer are console programs and are started without a console window. The sign-in entry starts the same executable as a supervisor, `kanade-engine.exe --supervise`, one per endpoint. It starts the engine as its child, records every exit code and every restart, and waits one second before the first restart and up to thirty while failures follow each other within thirty seconds. An engine started by other means is left alone and taken over once it ends. The engine holds a lock on its data directory and the first instance of its pipe, and exits with its own code when either is taken. Exit code 1 has its reason in a `fatal-` record, 101 is a panic that ended the process, and any other value was imposed from outside.

A peer that cannot be accepted says nothing about the next one. A host that opened the pipe and ended, or one that fails the user and session check, is refused alone. Only a listener that stays unable to offer a pipe instance ends the engine, so that a new process can take the endpoint; a process nobody can connect to is worse than none. A connection's slot and its engine session are released when its thread ends, however it ends, and a refusal at the connection limit is recorded. A panic while the engine handles a request ends that turn only. The waiting connection is closed at once, every session is dropped and the worker is replaced, which frontends already recover from by holding and restoring their compositions. More than four panics within a minute end the process instead. A frontend checks that its connection is still open before each key, on Windows as on macOS, so after a restart it reconnects first instead of passing that key on as a plain letter. While no engine is reachable the macOS frontend passes idle keys on.

In Windows hiragana mode, TestKeyDown checks the field before consulting the engine. Connected and offline input use the same check. The TIP passes the key to the application for a read-only document (`TS_SD_READONLY`), a read-only range (`TSATTRID_Text_ReadOnly` set to `VT_BOOL` true), a disabled keyboard compartment, or a password or PIN scope, including numeric passwords and alphanumeric PIN setup. A failed edit session, an invalid scope object or a failed `GetInputScopes` call also passes the key. In each case the TIP skips both the preceding-text request and the call to the engine. An enabled `IS_PRIVATE` field permits conversion with `Privacy::Private` and no preceding text, including in applications that allow learning.

The TIP checks the range's read-only attribute and input scope independently. For either attribute, a missing property, a failed `GetAppProperty` or `GetValue`, or a `VT_EMPTY` value means the host left that attribute unspecified. This includes `E_NOTIMPL` from an ACP store's `RequestSupportedAttrs` or `RequestAttrsAtPosition`, `E_FAIL` from TSF's fallback scope property, and the empty values a Win32 EDIT can supply through the IMM32 bridge (CUAS). A field with neither attribute specified permits ordinary conversion when the document is writable and the keyboard is enabled. For a nonempty selection, two property ranges reported by `EnumRanges` establish a transition and the TIP passes the key even if `GetValue` describes only the first range. If the store cannot enumerate transitions, the TIP uses the value for the selection.

Once the host supplies a nonempty input-scope value, it must expose `ITfInputScope`. A failed cast, a failed `GetInputScopes`, or a positive count with a null list passes the key to the application. A successful call with zero entries leaves the scope unspecified. For a longer list the TIP inspects the first 256 entries at most. A password or PIN in that prefix takes precedence over `IS_PRIVATE`. If the prefix contains neither, conversion proceeds normally even when more entries follow.

The TestKeyDown prediction belongs to one key message. For character keys it applies the engine's policy to the current layout's `ToUnicodeEx` result, with flag 4 to preserve the keyboard's dead-key state. A key that yields no character, such as Shift+0 on a JIS layout, passes at Test. If Kana Lock makes a letter key produce halfwidth kana, it also passes while idle because only ASCII graphic characters can start conversion. A passed key stays passed on a repeated Test or on KeyDown.

KeyDown reports what it handled. A connected engine can decline a predicted key. Test also cannot foresee a lost connection, a denied read lock or a focus change before delivery. KeyDown rechecks the field and uses the stricter scope for learning. If the field has become protected, the TIP passes the key to the application even if Test claimed a conversion starter during an outage. During conversion it drops the session and ends the mark with the displayed text intact when the host grants the write. In the test store, making the whole document read-only prevented the mark from ending. A focus reset expires the prediction. In a WPF TextBox, a declined Down can still run a command such as Backspace, Enter, Left or Space. For a letter already marked `ImeProcessed`, WPF can skip character generation even when Down passes, and the letter can be lost.

Outside reentry, if the host denies the scope read at Test or Down during composition, the TIP drops the session and requests the end of its mark in the original context. It preserves the displayed text and requests a deferred end of that same mark if the synchronous write is refused. Backspace, Enter, Escape and Space pass on the first press. If the read fails on a conversion starter, Down passes it, even when Test predicted a connected conversion. Down consumes it only when Test claimed it to drop it while the engine was unreachable.

A WPF probe routed the TSF calls from `TextServicesManager` to the test TIP, with the composition in the test store. After a refused scope read, Enter activated the default button and Escape activated the cancel button in a single-line TextBox. In a multiline TextBox, Enter inserted a newline and Space inserted a space. Ending the mark in a WPF or CUAS control remains unmeasured.

When Test or Down requests the end of a mark after protection or a refused scope read, the TIP is still outside its busy state. If the host grants the synchronous write and pumps pending input during it, a buffered key can start a new composition before the application receives the passed key. Always deferring the end could deliver the committed text after the passed key in a host such as CUAS that forwards composition text only on completion. Both orderings remain unmeasured in real hosts.

The key sink tracks each held key by virtual key, scan code and extended-key bit. Once any Down passes to the application, its Up also passes. A negative TestKeyDown counts immediately because the host may omit KeyDown. The TIP takes Up only for a press whose Downs it consumed, including Downs accepted into the reentry queue. The record survives a focus or mode change and is discarded when the sink detaches. An unknown Up passes.

On each Down the sink retires records whose virtual key is up in `GetKeyState`. WPF calls the sink after retrieving the message, when the thread's keyboard state reflects it. The timing in TSF's own hook is unverified. A fresh hook press with a scan code and bit 30 clear closes the old record for that key even if the sink missed its release. WPF supplies left and right Ctrl as distinct virtual keys. For Shift it supplies `VK_SHIFT` and scan code 0x2A or 0x36, with bit 30 clear even on repeats. Each repeat looks like a fresh press. The TIP passes every standalone Shift Down, so its Up also goes to the application.

With message scan codes and the extended bit, the sink can distinguish the main and keypad Return keys. Releasing either can clear their shared `VK_RETURN` state. If another Down intervenes before the second release, it can retire the remaining record and the second Up passes. WPF supplies identical arguments for both Return keys, so when their Downs have different destinations, both releases pass.

The TIP can notify the engine of a passed-through Backspace at Test, since KeyDown may never arrive. Repeated tests of the same message share that notification. In a probe using posted messages and a custom `WH_GETMESSAGE` hook, `GetMessageTime` retained the key message's timestamp. The WPF source calls TestKeyDown once on its key-down path. A host that processes another message and then tests the old press again can still notify twice. TSF supplies no unique press identifier, and distinct messages can have the same timestamp.

When a Windows host refuses the write lock, the composition or the text edit, the TIP acknowledges the failed edit with `applied=false` and drops that engine session. A composition veto can return `S_OK` with a null interface. The TIP ends any mark it owns, preserving the text already in the document. If the cleanup lock is also refused, it requests a deferred end for that same mark. The next key in a writable field starts a fresh session. Once the text edit succeeds, a caret positioning failure still allows a positive acknowledgement.

When the application terminates the TIP's composition, its completion or cancellation determines what stays in the field. The TIP discards its reading and closes the session without requesting a commit. When focus ends or Enter finishes a held reading, the TIP can write that reading only into its existing composition and only if the range still contains the last displayed text. If the application changed the range, the TIP ends the mark and leaves its contents in place.

TSF can deliver a key inside a text edit or after the store releases its lock, before `RequestEditSession` returns. For the same field the TIP uses the reply's ownership policy and the last checked field scope. For another field it queries scope without reading text. A locked scope read gives the key provisional private scope until delivery. KeyDown queues the translated key, field scope, target context and focus epoch. Once a conversion starter is queued, the composing key policy applies to subsequent keys for that context and focus epoch. Enter, Backspace, Space and arrows then follow the starter, including in a newly focused field. The engine reply supplies the policy once the starter is processed.

Physical and preserved input-mode commands join the same queue. After a mode command, the TIP claims translatable keys in eligible fields until the queue drains. Each key sees the mode established by the commands ahead of it. Modifier-only presses and other keys without a translation pass to the application and leave the queue untouched.

After the outer edit and its ACK attempt, the TIP processes unsubmitted actions in delivery order for each field. Scope checks retain the strictest classification from Test through delivery, including a fresh check under the current connection's learning policy. Password and read-only fields bypass the engine. If the host refuses the scope read for a queued key, a candidate click or a candidate poll, the TIP keeps the session and the acknowledged mark. It reports the discarded key or click and skips a refused poll for that update. This also applies to clicks and polls delivered outside reentry. An application-terminated mark or a rejected edit ends its engine session. The next queued key in that field starts a fresh session. After a lost ACK a queued character restores the reading from the applied edit before submission, and a queued Enter can finish the displayed conversion locally. The TIP never resends the uncertain event. Loss of a queued reply in the focused field uses the same outage hint and supervisor probe as a dropped starter.

On focus change or loss of foreground keyboard focus, the TIP checks whether the departing context is still on its original document manager's stack. While attached, that field drains its own queued keys and valid candidate selections on its session before finishing its remaining reading. Enter takes its turn even after a candidate click or refinement timer. Polls for a departing candidate list expire. The TIP checks the owned range before replacing its text. If the host ends the mark, its edit stands and any unsubmitted key for that attached field uses a fresh session there. After a Pop removes the context from the stack, its remaining actions expire and discarded keys trigger the notice. Input for the newly focused field waits for its own session and scope check.

Once KeyDown has returned TRUE, TSF offers no way to return that queued key to the application. A known limitation of reentrant mode switching is that a key queued behind a switch to direct input is discarded when its turn arrives. The engine can also decline a queued key (`consumed=false`), for example a second Enter after the first committed the conversion. Both cases produce a discard notice. A field that became protected or a candidate click whose handle expired can also leave an action unapplied.

The TIP shows one five-second notice when the queue drains. It uses the first discarded action's caret or focused-window rectangle, captured when the action was queued, to place the notice at the lower-right corner of that monitor's work area. If neither rectangle was available, it uses the primary monitor. The notice contains no input. UILess and secure activation suppress native notices.

TestKeyDown checks the connection even on the first eligible key after a focus change. Connected input follows the engine's key policy. When disconnected and idle, the TIP drops only a key whose actual keyboard translation would start conversion while connected. Secure activation permits connected conversion and passes idle keys during an outage. With no prior Test, a reconnected engine can decline the key. A dropped starter leaves the document and selection intact. A lost reply is never replayed, and a timed-out exchange gets no second handshake on the same key. The caret hint stays visible for five seconds. During a continuing outage the next drop at least ten seconds after the last successful display shows it again. A failed display can be retried on the next drop, and a successful key exchange rearms the hint immediately. UILess hosts suppress it.

Only a missing installed pipe when delivering a starter can request the adjacent `kanade-engine.exe --supervise`. The TIP schedules the launch in the background and waits ten seconds after an attempt before trying again. Unloading and reloading the DLL resets that interval within the same process. This can add launch attempts. The supervisor's named mutex still limits it to one instance per endpoint. The host must have an ordinary unelevated desktop token. Windows builds the user's environment and the TIP removes every variable beginning with `KANADE_`, case-insensitively. It creates the supervisor suspended with job breakaway and normal priority, checks that the child belongs to no job, then resumes it. A failed check terminates the suspended child.

`KANADE_INSTANCE` names an isolated engine on Windows. The label becomes part of the pipe name, and tests and measurements set it together with `KANADE_DATA_DIR`. Frontends never read it, so they always reach the installed engine.

The default configuration has neither live conversion nor a language model. The optional local model reranks existing Mozc candidates in a separate CPU worker, with a bounded background queue. Model import requires explicit license and local-processing consent, a pinned file digest, independent tokenizer parity, ranking fixtures and latency gates. Qualification binds the model, vocabulary, runtime executable, prompt and corpora; changes require qualification again. The Windows and macOS installers include the pinned model for offline import. [Local model details](llm.md) describe the limits and qualification procedure.

Kanade builds the Tsumugi prompt, vocabulary fingerprint, end token and qualification rules into the engine and worker. The settings window displays the fixed identity and binds consent to its terms. Import verifies the exact GGUF digest before running qualification. When Settings requests activation, the management thread saves that preference before recording the import and measuring the model. The service starts using the model after qualification passes. At engine startup, an enabled model with current consent and missing or obsolete qualification is measured in the background. Native controls save only the fields edited so they cannot overwrite activation or an unrelated change. Model status identifies whether saved consent covers the current model and terms.

After acknowledging its key reply, the frontend polls for candidate refinement. A focused native frontend may also send the next event sequence to receive and acknowledge a sentence preview. Sentence exploration runs in a background Mozc process with a temporary profile. It checks that the reconstructed segments match the visible conversion before submitting alternatives to Tsumugi. A stalled probe leaves the live worker, displayed composition and input connection available. The diagnostic events `probe-call-timed-out` and `probe-call-failed` identify failures of this optional worker. A key request whose deadline expires before its next Mozc command records `worker-request-expired-before-send`. The shared worker continues serving other sessions. A disposable probe can own an unfinished temporary session, so it is discarded on `probe-request-expired-before-send`. Without a confident whole-reading correction, the frontend receives the normal candidate order. A candidate-only response preserves the key sequence. A sentence preview advances it and follows the document acknowledgement protocol. A new revision retires old candidate handles. New keys, manual navigation, focus changes, resets and expired results cancel refinement. Native frontends poll every 60 ms while the result is pending and stop after the 700 ms scoring deadline with a small scheduling margin. The candidate footer reports active scoring, completion (including an unchanged order), a failed evaluation, or expiry. Terminal status alone preserves the candidate handles. Inference never delays the synchronous key response. Normal, non-excluded contexts with learning enabled may submit a bounded left context; private, unknown, password and sensitive contexts do not. Native candidates are independent of GPUI; settings UI exists only while a user window is open.

For a reading containing a Japanese comma or period, the engine compares alternatives within a single clause. Separators and the displayed text outside the clause are copied unchanged. In an empty field, a single final Japanese comma or period is held outside the verb comparison and restored after scoring, whether Mozc attaches it to the verb or gives it its own segment. The worker receives the clause reading and eligible left context and retains its existing request limits. When calculated dates are enabled, the first conversion can also format a spoken calendar year spanning several Mozc segments. The date candidate is labeled separately and skips approximate quantities and durations.

hasami analyzes acknowledged corrections on the learning thread, classifying term shape before records are updated. Its kana normalization also supplies keys for correction learning, project vocabulary and emoji lookup. It does not replace Mozc's conversion engine. Reading-constrained analysis of newly generated model output remains unimplemented; the current model produces scores for existing candidates only.

The signed IMK bundle declares its bundle-scoped `.Connection` service in `InputMethodConnectionName`. Startup reads this value from the bundle and rejects a mismatch with its bundle identifier before starting the server. The signed-bundle self-check validates the same configuration. An unrelated legacy connection name can leave native clients unable to obtain the IME endpoint even when another host can type.

Each IMK controller retains its settings menu and item for its lifetime, preserving their identity during repeated system-menu requests. The controller implements the custom settings action and the legacy Preferences callback using the same launcher. Menu enabling is explicit. On the qualified macOS version, InputMethodKit invokes the action directly rather than the controller's `doCommandBySelector:commandDictionary:` override; the action's dispatch event is the delivery evidence. LaunchServices activates the bundled settings application; a reopen callback reuses its window. The window is created before background configuration and model-status requests, so connection failures remain visible and retryable. The candidate selection and correction records tab requests one page at a time and keeps navigation and pagination above the scrolling list. Until settings load successfully, default values cannot be saved. macOS settings lifecycle diagnostics accept only predefined events, timestamps and process IDs, with a bounded private file per component. Selector names and command dictionaries are never logged. Menu construction performs no diagnostic I/O because the system can request the menu during ordinary input. Diagnostic writes occur only during explicit settings actions or settings-window lifecycle.

The settings window answers every explicit open request. GPUI forwards a reopen request only while no window is visible, so a window on another Space or display would not be shown again. The settings application therefore registers its own handler for the reopen Apple event; GPUI's callback remains as a fallback. A new window opens on the display under the pointer rather than always on the primary display. A later request restores a minimized window, and moves a window from another display, or from outside every display, to the pointer's display. A window already reachable there keeps the position the user chose, and a full-screen window is never moved. The window follows the active Space on activation and is ordered front within the normal level even before the application becomes active. It never raises its level, so another application's always-on-top window can still cover it. Native frame and ordering changes run outside GPUI updates because AppKit notifies GPUI's window delegate synchronously. Display selection and repositioning are pure functions with multi-display tests. Shortly after presenting, the window records whether it is visible, fully occluded or off the active Space, using predefined events only. An application menu provides Close, Minimize and Quit.

Local macOS updates require finished composition. The installer validates and stages a signed bundle before selecting an already enabled ASCII layout when Kanade is selected. Fresh helpers deliver TIS notifications before reading the selection cache and confirm the change with a bounded wait. A failed confirmation prevents bundle replacement. Updates normally terminate the matching IME and settings applications, then replace the bundle and restart the engine. Successful updates leave ASCII selected; a concurrent user selection is retained. Failed updates attempt to restore the original mode and report an unconfirmed restoration. A per-directory file lock excludes concurrent installers. Full composition/ACK draining and interruption recovery remain separate qualification work.

Input-source diagnostics filter the unqualified system-enabled list by bundle identity. A bundle-filtered query can include a mode that has no enabled record after a mode-ID migration. Diagnostics report the enabled mode IDs explicitly. An already enabled parent without its input mode is reported as stale; automatic enabling refuses that state and directs the user to remove and re-add Kanade in System Settings. Registration never toggles an existing mode off and on to repair it: that legacy API sequence can rewrite unrelated source preferences from a stale snapshot.

The [private worker protocol](worker-protocol.md) provides a dictionary-only background loader that preserves conversion/prediction history. Its generation-scoped status is independent of input event sequencing. Ordinary upstream protocol messages and the pinned source tree remain unchanged. Authenticated management serializes explicit edits through a lazily started background service. It compares the expected file revision, holds a writer lock, and prepares an immutable, synced replacement without dropping unknown protobuf data. The engine admits only its atomic rename, after every composition and document acknowledgement completes and input has been idle for two seconds. Cancellation races with publication through one atomic permit. Parsing, hashing, file/directory sync and cleanup stay on the management thread. Writer guards explicitly unlock before closing their file: a concurrent process spawn may briefly inherit the open file description. Jobs retain metadata only; a saved revision distinguishes failed reloads from unsaved edits. Explicit promotion reads an acknowledged correction record. Automatic promotion remains disabled pending ranking-budget measurements.

The native settings dictionary panel uses that same authenticated management service on background tasks. An in-memory draft is bound to the exact revision and entry/dictionary positions it displayed; refresh never rebases it onto a different revision. Submission freezes its fields, and an unknown result is not automatically replayed. Polling distinguishes an unsaved failure from a saved file whose engine reload failed. Correction records can prefill a registration form, but only an explicit Save submits it. Text fields implement native UTF-16 selection, marked text and candidate geometry; publication is blocked while a field is composing. No draft is written to diagnostic logs or autosaved. Closing an editable draft requires an explicit discard choice.

Learning defaults to all known application identities, except those in `learning_excluded_apps`. The authenticated exclusions operation compares the exact previous exclusion list under the settings lock and merges only that list into the current configuration; the former allowlist operation is refused rather than reinterpreted. A stale draft cannot overwrite another app-scope edit or unrelated settings. The native editor requires review, invalidates it on edits, blocks submission during marked text and freezes a submitted draft. It reads an uncertain outcome back without replaying it. Closing an unsubmitted draft presents a fixed, visible discard choice. The macOS chooser reads the selected bundle's identifier without loading its code.

Welcome adds an optional learning policy with an enabled flag and exclusions, retaining an empty legacy allowlist so an older frontend fails closed. Engine privacy gates enforce exclusions before any key, selection or restore reaches Mozc, and again before ACK-based learning, so stale clients cannot continue to learn in an excluded application. Applying an exclusion also clears pending selection intents, correction state, ephemeral left context and queued refinement for that session.

On Windows, input hosts may connect from the current user and logon session, including AppContainer hosts. A frontend connects only after it has checked which program serves the pipe, as which user and in which session, and for that it opens the serving process and its token. A packaged application may not open another process by default, so a text service in an AppContainer could open the pipe and still never convert. When it starts, the engine therefore grants every package two rights on itself and nothing more: the limited query right on its process, which shows the image name, the command line, the exit status and the time and I/O counters, and the right to read its token. Neither allows reading its memory, waiting for it or changing it. The counters move with every request, so a sandboxed process that polls them can tell when the user types, though not what; a password field never reaches the engine. If the grant fails the engine records `sandboxed-hosts-unreachable` and serves every other host. The program is compared by its native path, such as `\Device\HarddiskVolume3\Program Files\Kanade\kanade-engine.exe`: a sandboxed process may not see the drive letter of every volume, and the system then reports the image of another process by its native path, which a path with a drive letter never matches. The text service and the settings application derive the engine's native path from the file they were loaded from, which needs no drive letter, and compare it with the serving process's native image name, ordinally and ignoring case. Settings and stored-learning management additionally require the client process to be the installed sibling `kanade-ui.exe`, identified through the pipe's kernel-reported process ID. Conversion access alone does not grant management access.

The Windows text service adds one language bar item, the input-mode button `GUID_LBI_INPUTMODE`, which the taskbar input indicator has shown since Windows 8. The button's state is the open/close and conversion-mode compartments, so it holds no input. A click writes a compartment; the existing compartment sink updates the frontend and tells the item sink to read the icon and text again. The icon is drawn the first time it is requested for a mode, an icon size and a theme, and kept: あ or A in the regular weight and in the colour of the taskbar text for the light, dark or contrast theme. DirectWrite draws it with grey-scale smoothing, as the taskbar draws its own text, and GDI draws it where Direct2D cannot. An outline in the opposite colour would keep a stale icon legible, but on the real taskbar it showed as a halo around a heavy glyph, so nothing is drawn around the glyph. Nothing reports a theme change to a text service. The button therefore reads the theme again when the thread regains the keyboard focus and, at most once a second, when a key arrives. No icon resource and no window that listens for theme changes are needed. A left click toggles the mode. A right click opens a popup menu owned by the focused window of the host thread, without sending it a command. The menu runs a message loop, so the button reads its state again afterwards and does nothing once the text service is deactivated.

The menu starts the settings application from the host process: the installed sibling `kanade-ui.exe`, without a console window and outside the host's job when the job allows it. The application then runs with the host's privileges and environment, so an elevated host starts it elevated. The menu item is disabled in an AppContainer or low-integrity host, in a system process and on the secure desktop, where the application would inherit a sandbox or the system account; the Start menu shortcut remains available. Starting it through the engine, which runs as the plain user, would serve every host alike. That needs a protocol request and is not implemented.

The settings executable is a console program because of its command line, and Windows gives a console program a console, shown as a terminal window, when Explorer or the Start menu starts it. The packaged executable declares the console allocation policy `detached` in its manifest: Windows 11 24H2 and later then open no console, while a shell that starts the program still shares its own. A program holds one manifest and GPUI embeds its own while linking, so the packaging step merges the policy into that manifest with the SDK's manifest tool and checks that GPUI's settings, such as the DPI awareness, are still there. Earlier Windows versions and unpackaged builds do not have the policy. There the program, started without arguments, releases a console that no other process uses, which closes the terminal window a fraction of a second after it appeared.

Windows build tooling retains canonical filesystem paths internally and converts Git and Bazel path arguments from the Win32 verbatim namespace to forward-slash drive or UNC paths. The Windows input profile names its brand icon by a file and a position among that file's icon groups. Windows reads it for the input switcher and the taskbar's input indicator. The profile is one of the shared registrations and keeps the path of the DLL registered last, so both DLLs carry the same icon as their only icon group; either registration order then shows the same icon. `kanade-winres` renders the icon on the build host from the input-source template, in the form Microsoft requires of a brand icon, and writes the binary resource file itself. The TIP's build script hands that file to the linker, which converts it. No resource compiler or SDK tool takes part, so a Windows target can still be checked from another host.
